# ADR-0001. DDNS через делегирование подзоны своему NSD

- Статус: принято (ретроспективно, решение уже в коде)
- Дата: 2026-11-07
- Контекст: spec/problem.md §1.1 «Задача»

## Проблема

Домашняя площадка живёт на динамическом IPv6: провайдер периодически меняет
префикс. Имена должны следовать за адресом без ручных действий и без доступа
к панели регистратора.

Дополнительные требования, выяснившиеся по ходу:

1. Имена нужны разные по роли: внутреннее (leaf, SSH, шлюз) и публичное
   (Let's Encrypt, Telegram). Внутреннее не должно зависеть от зоны регистратора.
2. Хостов несколько, у каждого свой набор имён; удаление хоста должно убирать
   его имена, а не оставлять мусор.
3. Одна и та же машина может объявлять имена в разных зонах.
4. Новый проект должен заводиться одним именем, без правки кода.

## Варианты

| Вариант | Плюсы | Минусы | Вердикт |
| --- | --- | --- | --- |
| API регистратора (hostline) | имена сразу в основной зоне | API закрыт DDoS-Guard, автоматизация невозможна | отвергнут |
| Ручное обновление в панели | не нужен свой DNS | задержка в часы, человеческие ошибки, не масштабируется | отвергнут |
| Внешний DDNS-провайдер (dyndns и подобные) | готовое решение | имена вне нашей зоны, лишняя зависимость, платно за несколько имён | отвергнут |
| Делегировать всю зону iv77msk.ru на свой NSD | один источник истины | на регистраторе живут почта и прочее; риск для основной зоны несоразмерен | отвергнут |
| Делегировать подзону своему NSD, хосты публикуют себя сами | полный контроль, автоматизация, изоляция риска | второй DNS-сервер, единая точка отказа | **принят** |

## Решение

**Делегирование.** Регистратор получает NS-запись на подзону, дальше зона
живёт на нашем сервере:

    h      NS  ns.iv77msk.ru.      (домашние имена)
    plb    NS  ns.iv77msk.ru.      (имена контуров проекта plb)
    ns     A   46.17.42.198

**Публикация.** Каждый хост объявляет свой набор имён по SSH; приёмник на
шлюзе ведёт состояние и перегенерирует зоны.

**Имя как путь.** Имя имеет вид «запись.зона», зона — последняя метка, которая
разворачивается в «зона.iv77msk.ru». Зоны не фиксированы в коде:

    tg.d.plb     -> зона plb.iv77msk.ru,   запись tg.d
    ssh.h        -> зона h.iv77msk.ru,     запись ssh
    max.p.safer  -> зона safer.iv77msk.ru, запись max.p

**Декларативность.** Набор имён хоста — это полный набор, а не журнал
добавлений. Приёмник заменяет файл состояния хоста в каждой затронутой зоне;
пустой набор удаляет имена во всех зонах.

**Проверка изменений.** Отправитель раз в 10 минут (таймер systemd) сравнивает
адрес, имена, политику и NS с сохранённым состоянием и обращается к шлюзу
только при изменении. В строке состояния есть версия схемы, чтобы правка
формата заставила все хосты переотправить данные.

**Регистрация зоны в NSD.** Зоны перечисляются в конфиге, который приёмник
генерирует из состояния. `nsd-control addzone` отвергнут: его второй аргумент —
pattern, а не путь, а зоны, добавленные в рантайме, теряются при рестарте NSD
(см. ADR-0004).

## Последствия

Проще: смена префикса лечится за минуту; новый проект заводится одним именем;
удаление имени — правка реестра; хосты не знают друг о друге.

Сложнее: появился второй DNS, за которым надо следить; делегирование каждой
новой зоны — ручная операция у регистратора; шлюз стал единой точкой отказа
для всех имён сразу.

Принятые риски: одна машина обслуживает все зоны; при её падении имена
продолжают резолвиться из кэшей до истечения TTL, но обновляться перестают;
почта и основная зона не затронуты, потому что не делегированы.

## Что заставит пересмотреть

1. У регистратора появится рабочий API — появится смысл писать прямо в
   основную зону и убрать прослойку.
2. Появится вторая площадка для DNS — тогда вступает в силу резервирование,
   и схема обновления должна уметь два приёмника.
3. Потребуется DNSSEC — придётся пересмотреть генерацию зон: подпись ключами
   несовместима с текущей перегенерацией файла целиком.
4. Число зон вырастет настолько, что ручное делегирование станет узким местом.
