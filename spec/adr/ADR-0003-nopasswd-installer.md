# ADR-0003. Установка без интерактивного sudo

- Статус: принято
- Контекст: spec/install.md §4.1, spec/pitfalls.md §6.2

## Проблема

Установка ходит на хосты по ssh и выполняет привилегированные действия.
Интерактивный sudo в середине работы ломал две вещи:

1. `ssh -t` держал псевдотерминал всё время установки, локальный терминал
   оставался в raw-режиме, и вывод превращался в мусор (наблюдалось как `== 59:`).
2. Подтверждение sudo в Ubuntu привязано к терминалу (`timestamp_type=tty`),
   поэтому `sudo -v` в одной сессии не даёт прав в другой.

## Варианты

| Вариант | Плюсы | Минусы | Вердикт |
| --- | --- | --- | --- |
| Интерактивный sudo в одной сессии | ничего не настраивать | ломает вывод, требует pty | отвергнут |
| `sudo -S` с паролем в stdin | без pty | пароль через поток, плохой аудит | отвергнут |
| Python-обёртка с pty | «красиво» | та же pty-проблема плюс новый язык | отвергнут |
| `Defaults timestamp_type=global` | просто | меняет политику безопасности системы | отвергнут |
| **NOPASSWD на один установщик** | без пароля и pty, узкое правило | нужна одноразовая подготовка | **принят** |

## Решение

`make bootstrap-host HOST=x` кладёт скрипты в `/usr/local/lib/host2ns` и
создаёт `/usr/local/bin/host2ns-install.sh` — диспетчер на два действия
(`sender`, `ns`). В sudoers разрешён только этот файл:

    ilvin ALL=(root) NOPASSWD: /usr/local/bin/host2ns-install.sh

Дальше `make host2ns` вызывает `sudo -n … host2ns-install.sh` без терминала.

## Последствия

Проще: установка неинтерактивна, вывод чистый, годится для автоматизации.
Сложнее: обновление кода требует повторной подготовки хоста; появилось
постоянное правило sudo, которое надо держать узким.

## Что заставит пересмотреть

1. Понадобится обновлять код без пароля — тогда публикация пакета в
   root-каталог с проверкой контрольной суммы.
2. Хостов станет много — понадобится централизованное управление доступом.
