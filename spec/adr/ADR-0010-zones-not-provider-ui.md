# ADR-0010. Зоны — у своего NS, а не в UI/API DNS-провайдера

- Статус: принято
- Контекст: ADR-0001, ADR-0002, ADR-0004, `spec/zones.md`

## Проблема

Можно держать зоны у DNS-провайдера/регистратора и править их через
веб-интерфейс или API. Для домашней динамики это плохо: ручные правки,
чужая зона, нет политики/состояния/отката.

## Варианты

| Вариант | Плюсы | Минусы | Вердикт |
| --- | --- | --- | --- |
| Веб-UI провайдера | не надо VPS | хрупко/сложно; ручные ошибки; нет состояния/политики/аудита; не знает IPv6/NAT | отвергнут |
| API провайдера | автоматизация | токены/вендор/лимиты; чужая зона; нет `nat` из `SSH_CONNECTION` | отвергнут |
| **Свой NSD + зоны из состояния** | контроль, политика, restore/status | нужен VPS/NS | **принят** |

## Решение

У регистратора — только `NS`-записи и glue (делегирование). Зоны — на своём
NSD; изменения только через состояние отправителей/`host2ns`, не через
веб-панель. `make status`, `make restore`, `make prune`, `zonegen`.

## Последствия

Проще: правки воспроизводимы, есть состояние/политика/аудит, `nat`/IPv6
работают, провайдер не влияет на зоны.
Сложнее: нужно держать VPS/NS, обновлять NSD, следить за NS/glue.

## Что заставит пересмотреть

1. Провайдер даст полноценный API с политикой/состоянием (маловероятно).
2. Свой NS станет дороже/сложнее, чем управляемый DNS.
3. Появятся требования, которые NSD не закрывает.
