# 4. Установка

## 4.1. Две фазы

| Фаза | Команда | Пароль | Что делает |
| --- | --- | --- | --- |
| подготовка | `make bootstrap-host HOST=x` | да | код в `/usr/local/lib/<NAME>`, правило sudo |
| применение | `make host2ns` | нет | ключ, имена, политика, юниты, публикация |

Разделение введено потому, что обновление привилегированного кода и изменение
данных — разные операции с разной ценой ошибки. Пароль остался только на первой.

`bootstrap-host` нужен **каждому** хосту, включая NS: он кладёт диспетчер и
приёмник. `bootstrap-nsd` — отдельный шаг, только установка и настройка NSD.
Обе команды требуют явный `HOST` и работают по SSH; локальная машина
указывается явно, например `HOST=user@localhost`.

`make nsd-who HOST=ns` — только диагностика: копирует `bootstrap-nsd.sh` и
запускает `--who-has-53`, который обходит все network namespace и печатает
владельцев 53. Пароль нужен, как у `bootstrap-nsd`.

## 4.2. Что делает `bootstrap-host`

Запускается только с явным `HOST` и только по SSH; локальная машина тоже
указывается явно (`HOST=user@localhost`).

1. Копирует `scripts/` на хост (в `/tmp`, без sudo).
2. Через `sudo` кладёт файлы в `/usr/local/lib/<NAME>` (root:root 755).
3. Создаёт `/usr/local/bin/<NAME>-install.sh` — диспетчер `sender|ns`.
4. Пишет `/etc/sudoers.d/90-<NAME>-install`:

       <user> ALL=(root) NOPASSWD: /usr/local/bin/<NAME>-install.sh

5. Проверяет правило через `visudo -cf` до вступления в силу.

## 4.3. Что делает `host2ns`

Для NS-хоста: `sudo -n <NAME>-install.sh ns` — приёмник, генератор зон, юнит
`<NAME>-zones.service`, связка с `nsd`, sudoers приёмника и файл
`/etc/<NAME>/base` с базой имён.

Для каждого хоста реестра установка идёт в два шага:

1. `sender --defer-publish` — ключ, `id`, `names`, `family`, отправитель,
   юнит; таймер не включается.
2. `authorize.sh` кладёт публичный ключ в `authorized_keys` NS с forced
   command приёмника.
3. `sender` — включает таймер, публикует и проверяет, что данные ушли.

Ошибка службы публикации останавливает установку: вывод журнала печатается,
код выхода ненулевой.

Хосты, убранные из реестра, не опрашиваются: `make prune` сверяет id в
состоянии с реестром и удаляет оставшиеся записи пустым набором.

Имена прежнего проекта (`yach-*`) и NS (`nsiv77mskru`) остаются в
состоянии, пока `make prune` не удалит их; `make status` показывает их
наравне с новыми. `make status` — приёмка: `ИТОГ: всё на месте...` только
когда имена соответствуют политике (см. §2.7, §3.6). `last` чистится
установкой, чтобы после `prune`/восстановления данные перепубликовались.

На существующем NS `bootstrap-nsd` не перезапускает NSD вслепую: он
сравнивает конфиг, сохраняет старый, находит старый unit/процесс (в том
числе в другом netns), останавливает только NSD и откатывается при неудаче
(ADR-0007). Адреса из старого main не дублируются (ADR-0008), иначе NSD
падает с `EADDRINUSE`, а `ss` пуст.

## 4.4. Идемпотентность

Повторный запуск не пересоздаёт ключ, не теряет состояние и не плодит юниты.
`bootstrap-host` перезаписывает код и правило sudo; `host2ns` — данные.
`bootstrap-nsd` тоже идемпотентен: установленный `nsd` не переустанавливается,
одинаковый конфиг не вызывает перезапуск, `reset-failed` снимает start-limit.
NSD слушает конкретные адреса хоста и loopback, поэтому `systemd-resolved`
не мешает; адреса, уже заданные в старом main-конфиге, не дублируются. VPS
может быть самым дешёвым: NSD нетребователен к памяти, зоны статические, без
БД (ADR-0009). Зоны живут на своём NSD, а не в UI/API провайдера; у
регистратора только `NS`/glue (ADR-0010). Если
NSD уже работает (unit или процесс старой установки), скрипт
находит его и по сокетам, и по процессам (сокет может быть в другом netns),
останавливает, применяет конфиг и запускает управляемый; старый конфиг
сохраняется и восстанавливается, если старт не удался. Перед стартом
проверяются дубли `ip-address` (`uniq -d`); при дубле конфиг откатывается.
Владельца 53 можно увидеть через `make nsd-who HOST=ns`; это нужно, когда
host-`ss` пуст, а bind падает. Старые зоны/конфиги
(`10-yach-zones.conf`) не дублируют новые: один конфиг на проект; иначе NSD
ругается на дубль зоны. `make status` после установки должен печатать
`ИТОГ: всё на месте и соответствует политике`.
Строка ключа в `authorized_keys` заменяется, а не дописывается: `authorize.sh`
удаляет прежнюю запись с тем же ключом. Установка очищает `/var/lib/<NAME>/last`
и тем заставляет отправителя опубликовать данные заново — иначе после `make
prune` или восстановления NS повторное добавление хоста осталось бы без DNS.

## 4.5. Имя и пути

Всё параметризовано одной переменной `NAME` (по умолчанию `host2ns`).
Диспетчер берёт её из собственного имени `<NAME>-install.sh`, поэтому путь к
установщикам (`/usr/local/lib/<NAME>`) не задаётся ещё раз в коде:

    /etc/<NAME>/..., /var/lib/<NAME>/..., /usr/local/lib/<NAME>/
    /etc/<NAME>/base — база имён, общая для юнита и приёмника
    <NAME>.service, <NAME>.timer, <NAME>-zones.service

## 4.6. Где упоминается имя

| Место | Что именно |
| --- | --- |
| файлы и каталоги | `/etc/<NAME>`, `/var/lib/<NAME>`, `/usr/local/lib/<NAME>` |
| юниты systemd | `<NAME>.service`, `<NAME>.timer`, `<NAME>-zones.service` |
| drop-in NSD | `/etc/systemd/system/nsd.service.d/10-<NAME>-zones.conf` |
| ключи хостов | `restrict,command="sudo -n /usr/local/bin/<NAME>-recv.sh"` в `authorized_keys`; строку пишет `authorize.sh` |
| sudoers | `90-<NAME>` (приёмник), `90-<NAME>-install` (диспетчер) |
| конфиг зон | `/etc/nsd/nsd.conf.d/10-<NAME>-zones.conf` |
| временные файлы NSD | `.00-<NAME>-old.*`, `.00-<NAME>-addr.*` рядом с `00`, не `.conf` |
| старый конфиг зон | `10-yach-zones.conf` — удаляется миграцией; один конфиг на проект |
| диагностика | `make nsd-who HOST=...` (`--who-has-53`) |
| скрипты на хосте | `/usr/local/bin/<NAME>*` |

Проверка после переименования:

    grep -rl "host2ddns" /etc/systemd/system /etc/sudoers.d /etc/nsd 2>/dev/null
    grep -o 'command="[^"]*"' ~/.ssh/authorized_keys | sort -u
